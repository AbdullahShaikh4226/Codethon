The project as we understand it

ProblemRTO is estimated as size ÷ bandwidth, which ignores friction: API latency, handshakes, disk hydration, throttling.
SolutionGradient Boosting learns real restore behaviour, predicts RTO, isolates cloud friction (forecast − physics), projects RTO across sizes, explains with feature importance and SHAP.
WorkflowOffline: clean, scale, train, save model + scaler. Online: workload vector → physics baseline → model → forecast, friction, curve, explanation.
Theme gapNo threat model in the deck. The security layer (incident type, breach cost) is designed in docs/GMCR_Pipeline.md.

5 · Proposed

Issue-source identification and flagging

Keep the site's tabs and workflow. Replace the fixed sentence with three levels of source, all driven by the model and the data.

L1 · FactorWhich input makes this forecast slow?

SHAP on a log-target model, folded back to the original inputs, read as multipliers. Replaces "AI Mitigation Recommendation" on the AI Orchestrator tab.

L2 · RecordWhich past restore went wrong?

Actual vs cross-validated prediction, robust z-score on the log residual, flag |z| > 3.5. New "Flagged restores" table on the Validation tab; Feedback entries scored on submit.

L3 · LocationWhere do problems concentrate?

Flag rate and friction per region, tier and transport mode. Colour the existing map. Hot when the rate is over 2× overall with at least 10 rows.

Flag rule: a controllable factor at ×1.5 or more is red, ×1.2 to ×1.5 amber. VM size is shown, never flagged. Each red factor gets a what-if re-run of the model. Tested on the AWS case above: st1 874 min → gp2 302, gp3 168, io2 103 min (model estimates).

L2 tested Data: flags 50 AWS, 43 Azure and 23 VMware restores out of 1000 each. Example: AWS i-ed98e0bb8ba4a9e5 took 146.0 min vs 128.7 expected (z = +4.6). With no root-cause labels, we cannot tell injected faults from noise; the plan includes an injected-fault test.

L3 caveat Data: Region has no measurable effect in any dataset, so no region will turn hot with the current data. Azure IDs do not help either: 1000 different subscriptions, all in resource group "Prod".

Code: L1 factor flags and what-if 
import numpy as np, pandas as pd, shap

def factor_flags(pipe, cat_cols, row: pd.DataFrame):
    """Return {input column: multiplier} for one workload, largest first."""
    pre, model = pipe.named_steps["pre"], pipe.named_steps["m"]
    Xt = pre.transform(row)
    sv = np.asarray(shap.TreeExplainer(model).shap_values(Xt)).reshape(-1)
    names = pre.get_feature_names_out()
    src = [next((c for c in cat_cols if n.startswith(c + "_")), n) for n in names]  # fold one-hot back
    mult = np.exp(pd.Series(sv, index=names).groupby(src).sum())
    return mult.sort_values(ascending=False)

def what_if(pipe, row, column, better_value):
    alt = row.assign(**{column: better_value})
    return float(np.exp(pipe.predict(row))[0]), float(np.exp(pipe.predict(alt))[0])

from sklearn.model_selection import cross_val_predict, KFold

pred = np.exp(cross_val_predict(pipe, X, np.log(y), cv=KFold(5, shuffle=True, random_state=0)))

Plain Gradient Boosting loses to Random Forest on the skewed Azure and VMware data. With a log target it is the best or close to it everywhere. R² of 0.99 and above means near-formula data, so tell judges it is likely synthetic.

Data quality issues

  • Category names differ from the site: data "Southeast Asia" vs site "SE Asia"; site "West US" not in data; data "us-west-2" vs site "us-west-1".
  • Inputs missing on the site: VMware Concurrency_Level (second-strongest driver) and Disk_Provisioning; Azure Vault_Redundancy.
  • 64,000 IOPS on gp3, gp2 and st1. Per AWS documentation (outside knowledge, not from the data): gp3 tops out at 16,000, and st1 and gp2 have no provisioned IOPS.
  • 49% of Azure restores beat physics because Instant restore mounts instead of copying. Use a method-aware baseline.
  • No timestamps, so Historical Trends cannot work. No incident type, so the security layer cannot be trained.
